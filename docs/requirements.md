| 項目 | 内容 |
|---|---|
| 作成日 | 2026-09-11 |
| バージョン | v1.0(再構築版) |
| 対象 | 独自配信(WebRTC/SFU) + YouTube配信集約 プラットフォーム |

---

## 1. プロジェクト概要

### 1-1. 背景
既存の実装(mediasoup + Socket.IO + YouTube連携)をベースに、設計を見直して
再構築する。既存実装のレビューで判明した設計上の課題(状態管理の不整合、
認証方式の重複等)を解消することを主目的の一つとする。

### 1-2. 目的
- 個人/小規模チャンネル運営者が、ブラウザから手軽に配信を開始できる場を提供する
- 自チャンネルのYouTube配信と独自配信を1つの画面に集約して表示する

### 1-3. 想定利用者
| 利用者区分 | できること |
|---|---|
| 配信者(登録ユーザー) | チャンネル開設、独自配信の作成・開始・終了 |
| 視聴者(未登録可) | 配信一覧の閲覧、配信の視聴、視聴者数の確認 |
| 視聴者(登録ユーザー) | 上記に加えプロフィール管理 |

## 3. 非機能要件

### 3-1. データ整合性(旧実装の反省を踏まえた要件)
- 配信の状態は **文字列区分(SCHEDULED / LIVE / ENDED)** で統一し、
  データソース(独自配信/YouTube)によって数値の意味が変わることを禁止する
- API・DB・フロントの型定義は単一の情報源(1箇所)から生成・共有し、
  実装ごとに個別定義しない

### 3-2. パフォーマンス
- 配信一覧取得のレスポンスは平均1秒以内(キャッシュヒット時)
- 同時視聴者数: 初期目標 50〜100人/配信(要協議、SFU1インスタンスでの目安)

### 3-3. 可用性
- mediasoup workerの異常終了時は自動再起動する(既存実装踏襲)
- バックエンドAPIとSFUシグナリングサーバーは分離してスケール可能な構成にする(将来課題)

### 3-4. セキュリティ
- 認証トークンはhttpOnly Cookieで管理し、JavaScriptから直接アクセスさせない
- パスワードは不可逆ハッシュ(bcrypt)で保存
- アップロードファイルはMIMEタイプ・サイズを検証
- CORSは許可オリジンを明示的に列挙する

### 3-5. 保守性
- 認証ロジック・トークン検証ロジックは重複実装を禁止し、1箇所に集約する
- 命名規則(ファイル名・関数名)を統一し、lintで機械的にチェックする

### 3-6. 運用
- Gitはmonorepo構成、Sourcetreeで管理(別途Git運用ルール参照)
- 環境変数は`.env.example`で必須項目を明示する

## 4. スコープ外(今回は対応しない)

- 配信のアーカイブ・録画機能

- 課金・投げ銭機能
- モバイルアプリ(ネイティブ)対応
- 多言語対応(i18n)

スコープ外項目は、将来のフェーズで別途要件定義を行う。

## 5. 用語集

再構築前の実装で用語の揺れ(`isLive`の数値の意味がソースにより異なる等)が
あったため、以降の設計・実装で使用する用語を以下に統一する。

| 用語 | 定義 |
|---|---|
| Stream | 独自配信・YouTube配信を問わない「配信」の総称 |
| Channel | 配信者が持つチャンネル(1ユーザー1つ) |
| status | 配信の状態。`SCHEDULED`(配信予定) / `LIVE`(配信中) / `ENDED`(終了) の3値のみ |
| source | 配信の提供元。`INTERNAL`(独自配信) / `YOUTUBE`(YouTube連携) |
| Producer / Consumer | mediasoup用語。配信者側=Producer、視聴者側=Consumer |
| viewerCount | 配信者自身を除いた実視聴者数 |

## 6. 技術選定表

### 6-1. 選定結果

| 領域 | 採用技術 | バージョン目安 |
|---|---|---|
| フロントエンド | Next.js (App Router) | 14系以降 |
| 言語 | TypeScript | 全レイヤー共通 |
| バックエンド | Express | 4系 |
| DB | PostgreSQL | 15系以降 |
| ORM | Prisma | 5系以降 |
| リアルタイム通信 | Socket.IO | 4系 |
| WebRTC SFU | mediasoup | 3系 |
| 認証 | JWT + httpOnly Cookie | - |
| 外部API | YouTube Data API v3 | - |
| ファイル保存(初期) | ローカルディスク | 将来S3等へ移行 |
| Git管理 | Sourcetree(GUI) | monorepo構成 |
| Lint/Format | ESLint + Prettier | - |
| CI | GitHub Actions | 将来導入 |

### 6-2. 選定理由・比較検討

| 領域 | 採用 | 主な代替案 | 採用理由 |
|---|---|---|---|
| フロントエンド | Next.js | Vite + React | ルーティング・SSRが組み込みで認証ガードと相性が良い |
| ORM | Prisma | TypeORM | スキーマファーストで型生成が強力、マイグレーション管理が容易 |
| 認証方式 | httpOnly Cookie | localStorage + Bearer | XSS時のトークン漏洩リスクが低い。旧実装で両方式が混在しバグの温床になったため一本化 |
| SFU | mediasoup | LiveKit / Janus | 旧実装の資産を活かせる、Node.js/TypeScriptとの親和性が高い |
| 状態管理(配信ステータス) | 文字列enum | 数値フラグ | 数値だと意味の取り違えが起きやすいことを旧実装で経験したため |

---

## 7. 制約条件・前提

- 開発者1名(個人開発/ポートフォリオ)を前提とした体制
- 本番運用の負荷は小規模(同時視聴数十人規模)を想定
- インフラコストを抑えるため、初期はVPS 1台での稼働を想定
